# 설계 — 블로그 글 목록 (티스토리 자동 수집 · `/blog` · 홈 「블로그」)

- 작성 2026-09-27 · 상태: 구현 완료, 배포 전
- 운영자 요청(2026-09-27): 「suhdp.tistory.com의 전체 게시물을 소개하는 화면을 만들어 줘요. 개별적으로 하니까 유인책이 없는 것 같아요.
  게시물의 요약 내용을 하나씩 보이게 최근 10개 정도 홈에 보이고 카테고리별로 열람할 수 있게.」 · 「인기 좋은 글은 별도로 볼 수 있게 홈 화면에.」
- 코드: `web/src/lib/blog/tistory.ts`(규칙·테스트) · `features/blog/{repository,sync,actions}.ts` · `features/blog/ui/*` · `app/(public)/blog` · `app/admin/blog`

## 0. 운영자 결정 (2026-09-27)

> 「인사이트를 작성하는 것보다 tistory를 자동으로 올리는 것이 편리할 것이라는 생각이 들었어요. 인사이트를 별도로 알리고 싶은 글이 있을 때마다 올리는 게 좋을 것 같아요.」

- **블로그 글은 자동 목록이 기본이다.** 운영자가 한 편씩 옮겨 적지 않는다.
- **인사이트(`/insights`)는 따로 알리고 싶은 글이 있을 때만** 올린다 — 골라 강조하는 자리다.
- 그래서 홈에서 「블로그」(전체·최신)가 「최신 인사이트」(골라 올린 것) **위**다.

## 1. 무엇을 어디서 읽나 (2026-09-27 실측)

| 필요한 것 | 원천 | 실측 |
|---|---|---|
| 전체 글 주소 | `https://suhdp.tistory.com/sitemap.xml` | 글 24편(PC·모바일 주소가 겹쳐 48줄) · 카테고리 주소 24줄 |
| 제목·요약·발행일·대표 이미지 | 글 페이지 `<meta>` `og:title` · `og:description` · `article:published_time` · `og:image` | 24편 전부 해석 성공(실패 0) |
| 글 번호·카테고리 | 글 페이지 `window.T.entryInfo` `{entryId, categoryLabel}` | 카테고리 8개(상위) — 티스토리 사이드바 글 수와 일치 |
| 공감 수 | `GET /reaction?entryId=N` → `data.reactionCounter.sum` | 0~4 |

- RSS(`/rss`)는 **최근 10편만** 준다(블로그 설정) → 「전체」에는 사이트맵이어야 한다.
- 조회수는 공개되지 않는다(티스토리 Open API 종료).
- ⚠ **`POST /reaction`은 조회가 아니라 공감 누르기다.** 조사 중 한 번 POST로 시험해 entryId 2에 공감이 1 올라갔다(3 → 4).
  DELETE로 되돌리려 했으나 권한 분류기가 막았고 우회하지 않았다 — 운영자 판단 대기. 코드는 GET만 쓴다(주석·테스트에 적음).
- 「개인정보처리방침-1」도 `/entry/`로 올라와 있다(글이 아니다) → 관리자 화면에서 **숨기기**로 내린다(자동 규칙을 만들지 않았다 — 제목으로 거르는 규칙은 깨지기 쉽다).

## 2. 규칙

- **요약**: 티스토리 자동 요약(본문 앞 약 400자)은 글 머리 장식 문구가 붙어 나온다(「2026.09.20 · CRYPTO MARKET크립토 …」).
  문장을 다듬어 「요약」을 지어내지 않는다 → 운영자가 `/admin/blog`에서 쓴 요약(`summaryOverride`, 200자)이 있으면 그것, 없으면 자동 요약을 그대로.
- **인기**: 티스토리 **공감 수** 많은 순, 같으면 최신. 공감 0·못 읽음(NULL)·숨김은 인기가 아니다.
  - 왜 공감인가: 모든 독자가 남긴 공개 신호다. 우리 사이트 클릭(`/go/blog-*`)은 **우리가 놓은 자리**가 만든다 — 그걸로 순위를 정하면 자리가 자리를 정하는 되먹임이 된다.
  - ⚠ 한계: 지금 0~4라 한두 표에 순위가 흔들린다 → 화면에 「기준: 티스토리 공감 수」와 각 글의 「공감 N」을 적는다.
- **카테고리**: 상위 → 하위 두 단계. 글 수 많은 순, 「미분류」는 맨 뒤.
- **링크**: 전부 `/go/blog-<글 번호>` 경유 — 목적지는 `BlogEntry.url`에서만(숨긴 글은 404). 클릭은 「티스토리로 넘어간 클릭」 합계에 그대로 들어간다(`OutboundClick`은 대상 구분 없이 합산).
- **수집**: 매일 06:00 예약 수집의 **맨 뒤**(`blog` 작업 — 거시·GCRM이 먼저 끝난다) + 관리자 「지금 수집」(같은 함수).
  새 글과 7일 넘게 안 읽은 글만 페이지를 다시 읽고, 공감은 매일 전부 읽는다. 동시 요청 4개. 결과는 `BlogSync`에 남는다.
- ⚠ 자동 수집은 `summaryOverride`·`hidden`을 덮지 않는다. 공감을 못 읽은 날은 어제 값을 둔다(NULL로 덮지 않는다).

## 3. 화면 (UI 권고 — 근거 · 대가)

**홈 「블로그」** — 조류 바로 아래, 최신 인사이트 위.
- 권고: 왼쪽 2/3 최근 10편(카테고리 · 날짜 · 제목 · 요약 두 줄), 오른쪽 1/3 인기 5편(순위 · 제목 · 공감 N), 머리 오른쪽에 「카테고리별 전체 N편 →」.
- 근거: 1순위 목적(티스토리 유입)의 길 · 초두 효과 · F자 훑기(왼쪽 목록이 먼저 읽히고 인기는 곁눈의 「다른 길」) · 목록형이 카드 3장보다 훑기 쉽다.
- 대가: 최신 인사이트가 한 칸 밀린다. 인사이트 기존 6편이 블로그 글과 같아 **당분간 같은 제목이 두 번** 보인다
  → 운영자 결정(§0)대로 인사이트가 「골라 올린 글」만 남으면 풀린다. 홈이 한 블록만큼 길어진다(10편 × 약 3줄).
- 확인: `/go/blog-*` 클릭 수. ⚠ 클릭 비교는 **10/03 이후**만 성립한다(9/18 자 교체 — 기억 `click-metric-reset-2026-09-18`).

**`/blog`** — 카테고리 칩(개수 표시) → 하위 칩 → 최신순/인기순 → 목록 → 블로그 대문 CTA.

**상단 메뉴** — 「블로그」를 「인사이트」 바로 뒤에(둘 다 티스토리로 가는 길).
- ⚠ 8개가 되자 768~1023px에서 글자가 두 줄로 꺾였다(로컬 눈 확인) → 가로 메뉴를 **lg(1024px)부터** 펼치고 그보다 좁으면 햄버거. 대가: 태블릿 가로(768~1023)에서 메뉴가 한 번 더 눌러야 보인다.

## 4. 배포 — 변경은 하나씩

| 조각 | 무엇 | 배포 전 가설 |
|---|---|---|
| A | 수집(표·예약·관리자) + `/blog` + 메뉴 + `/go/blog-*` | CHANGELOG (75) |
| B | 홈 「블로그」 블록 | CHANGELOG (76) |

A 뒤 운영에서 「지금 수집」이 워커에서 티스토리에 닿는지 먼저 본다(재무부 전례 — 워커에서 막히는 원천이 있었다). 닿지 않으면 GitHub Actions로 옮긴다.
B는 A의 자료가 있어야 보인다(없으면 블록을 그리지 않는다 — 배포 순서가 틀려도 빈 블록은 안 뜬다).
