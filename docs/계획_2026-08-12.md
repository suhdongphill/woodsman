### ⚠ A3. **속도 제한이 동작하지 않는다 — 최우선 과제**

> **2026-08-15 후속:** 아래 "남은 가설 1(OpenNext env 프록시)"은 **반증됐다.** 운영에는

> **이 항목의 최신 상태는 `docs/계획_2026-08-15.md` §2·§3에 있다.** 아래는 당시 기록으로 남긴다.

`/api/view` 무제한 쓰기(8/7 점검 지적)는 **아직 닫히지 않았다.** 닫힌 줄 알았는데 아니다.

**측정 결과** (2026-08-11 밤, 운영본)

| 시도 | 결과 |
|---|---|
| 순차 75건 (~75초) | 75건 전부 통과 (창을 넘겨서일 수 있음) |
| 병렬 120건 (7초) | **120건 전부 통과** |
| 카운터가 오른 뒤 병렬 120건 재시도 | **120건 전부 통과** |
| 누적 | **447건 전부 통과 · 차단 0건** |

**지금까지 좁힌 것**
- 바인딩은 붙어 있다 — 배포 출력에 `env.BEACON_LIMITER (60 requests/60s) Rate Limit`.
- `wrangler tail` 레코드 18건이 **전부 `logs: []`** → `[beacon] BEACON_LIMITER 바인딩이 없어…`
  경고가 **안 찍혔다.** 즉 `getLimiter()`는 객체를 찾았고 `limit()`이 매번 `success: true`를 준다.
- `cf-connecting-ip`는 정상 수신(`222.100.116.182`). 키가 `unknown`으로 뭉개진 게 아니다.
- 예외도 아니다 — 예외면 라우트가 `{ok:false}`를 돌려주는데 전부 `{ok:true,counted:true}`였다.

**남은 가설 (내일 이 순서로 확인)**
1. **OpenNext env 프록시가 RateLimit 객체를 제대로 넘기지 못한다** — D1은 되는데 RateLimit은
   스텁이 와서 `{success:true}`만 돌려주는 경우. `limit()` 반환값을 **한 번 로그로 찍어** 확인한다
   (`typeof`·키 목록까지). 가장 유력하다.
2. 문서상 "permissive · eventually consistent · **정확한 계수 시스템으로 쓰지 말 것**"이라
   설계상 이 정도 폭주를 못 막는 것일 수도 있다 → 그렇다면 **방어 수단을 바꿔야 한다.**
3. `namespace_id: "1001"`이 계정 내 다른 네임스페이스와 겹칠 가능성(낮음).

**가설 1·2가 확인되면 대안**
- 미들웨어(`src/middleware.ts`)로 옮겨 Worker 런타임에서 직접 호출 — 프록시를 건너뛴다
- 또는 **Cloudflare 대시보드의 WAF Rate Limiting 규칙**으로 `/api/*`에 건다(앱 코드 밖, 확실)
- ⚠ D1 카운터로 만들지 않는다 — 요청마다 쓰기가 늘어 막으려던 문제를 키운다

⚠ **현재 상태는 fail-open이다.** 서비스는 정상이지만 **누구나 조회수·체류시간을 만들 수 있다.**
그러니 `/admin/analytics`의 초기 숫자는 그만큼 덜 믿는다.
