# site-inspect — 사이트 운영·보안 점검

`점검해줘` 한마디로 **말과 실제가 같은지**를 대조한다.

기준 문서는 세 개다. 이 순서로 우선한다.

1. `docs/운영지침.md` — 왜 그렇게 운영하는가 (**최우선 기준**)
2. `docs/woodsman_개발요구서_v2.md` — 무엇이 있어야 하는가
3. `web/CLAUDE.md` — 어떻게 만들어야 하는가

⚠ 이 셋과 실제가 다르면 **어느 쪽이 틀렸는지 단정하지 말고 둘 다 보고한다.**
문서가 뒤처졌을 수도 있고 코드가 어긋났을 수도 있다. 판단은 사람이 한다.

---

## 0단계 — 준비 (사람이 할 일)

관리자 화면은 로그인해야 보인다. **먼저 사용자에게 요청한다:**

> 브라우저에서 <https://portfolio-solutions.net/admin> 에 관리자로 로그인해 주세요.
> (로그인 화면이 안 보이면 로고를 더블클릭하면 됩니다.) 되면 알려주세요.

- 로그인 확인 전에는 화면 점검을 시작하지 않는다. 대신 코드·문서 점검은 먼저 돌려도 된다.
- 사용자가 "로그인 없이 진행"이라고 하면 화면 점검을 **건너뛰고 그 사실을 보고에 적는다.**
  ⚠ 조용히 생략하지 않는다 — 안 본 것이 괜찮은 것으로 읽히면 점검이 거짓말이 된다.
- 로그인 자격증명은 **절대 대신 입력하지 않는다.** 사용자가 직접 한다.

## 1단계 — 사실 수집 (직접, 에이전트 없이)

에이전트에게 넘길 공통 사실을 먼저 모은다. 없으면 세 에이전트가 같은 일을 세 번 한다.

```bash
git -C "D:/P1.VideCoding/3. StockMng" log --oneline -10
git -C "D:/P1.VideCoding/3. StockMng" status --short
gh run list --limit 3                      # 자동 배포가 아직도 실패 중인가
cd web && npm run typecheck && npm run test # 지금 통과하는가
```

운영 경로 상태(실제로 살아 있는가):

```bash
for p in / /about /privacy /disclaimer /insights /journal /portfolio /macro /macro/bubble \
         /board /register /llms.txt /robots.txt /sitemap.xml /admin; do
  printf "%-18s %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' "https://portfolio-solutions.net$p")"
done
```

기대값: 공개 경로 200 · `/board`는 커뮤니티가 닫혀 있으면 **404** · `/admin`은 **307**.
다르면 그 자체가 발견 사항이다.

## 2단계 — 세 갈래 병렬 점검 (Workflow)

운영 점검과 보안 점검은 **전문성이 다르다.** 한 에이전트에게 다 시키면 둘 다 얕아진다.
`Workflow` 도구로 아래 셋을 병렬로 돌린다. 1단계에서 모은 사실을 각 프롬프트에 넣어 준다.

### A. 운영지침 점검 에이전트

> `docs/운영지침.md`와 `docs/woodsman_개발요구서_v2.md`를 읽고, 코드·설정이 그대로인지 대조하라.
> 특히:
> - **목업 부활** — `src/**`에서 `@/lib/mock`을 import하는 화면. 관리자 편집이 무효가 되는 자리다.
> - **죽은 버튼** — `onClick`·`action`·`href` 없는 `<button>`, `<span>`으로 만든 가짜 버튼,
>   `defaultOn`만 받고 `name` 없는 `Toggle`. 누를 수 있는데 아무 일도 안 하는 것을 찾아라.
> - **같은 판단의 중복 구현** — 화면과 서버가 각자 판단하는 곳.
> - **말과 동작의 불일치** — `lib/site-status.ts` 로드맵이 '예정'이라는데 실제 스위치가 열려 있는가.
>   `/privacy`가 "회원정보를 수집하지 않는다"인데 가입이 열려 있는가.
> - **모의/실계좌 표시** — 계좌 숫자가 나오는 화면에 `DataModeNotice`가 빠진 곳.
> - **수기 시세의 기준일** — 값만 있고 `priceAsOf`가 없는 표시.
> - **티스토리 우선순위** — 글 끝에서 광고가 CTA보다 위에 오는 곳.
> - 실명(필명 정책) — `/privacy` 책임자 외의 자리에 실명이 있는가.
> 발견마다 `파일:줄`과 **왜 문제인지**를 한 문장으로. 추측이면 추측이라고 적어라.

### B. 보안 점검 에이전트

> 이 저장소의 보안을 점검하라. 배포 대상은 Cloudflare Workers + D1이고, 공개 저장소다.
> - **유출** — 커밋된 시크릿(`.env`가 추적되는가), `NEXT_PUBLIC_` 접두사가 붙은 비밀,
>   소스에 박힌 API 키 리터럴, 관리자 이메일·계정 식별자가 공개 화면·번들에 나오는가.
> - **권한** — 모든 서버 액션(`"use server"`)이 `requireAdmin`/`requireUser`를 부르는가.
>   미들웨어만 믿는 경로가 있는가. 가입 폼이 `role`을 받는가.
> - **입력 경로** — 댓글·게시판 등 사용자 입력이 들어오는 모든 지점. 길이 제한, 정화
>   (`sanitize-html`이 허용 목록인가), SQL의 `?` 바인딩(문자열 연결이 있는가),
>   컬럼명을 사용자 입력으로 만드는 곳.
> - **리다이렉트** — 쿼리로 받은 URL로 이동하는 곳(오픈 리다이렉트).
> - **정보 노출** — 로그인 실패 사유 구분, 에러 메시지에 스택·쿼리가 실리는가.
> - **의존성** — `cd web && npm audit --omit=dev` 결과 중 실제로 이 앱 경로에 닿는 것.
> - **최신 위협** — WebSearch로 Next.js·NextAuth(Auth.js)·Cloudflare Workers/D1의
>   최근 공개 취약점을 확인하고, 이 저장소의 버전(`web/package.json`)이 해당되는지 대조하라.
> 발견마다 **심각도(높음/중간/낮음)**, `파일:줄`, **어떻게 악용되는지 한 문장**, 처방을 적어라.
> ⚠ 악용 코드를 쓰지 말고, 어디가 뚫리는지만 지목하라.

### C. 화면 점검 에이전트 (0단계 로그인이 확인됐을 때만)

> `mcp__claude-in-chrome__*` 도구로 <https://portfolio-solutions.net> 을 직접 본다.
> - 공개 화면: 홈·소개·투자일지·포트폴리오·거시 지표·버블 모니터가 뜨는가.
>   계좌 숫자 옆에 모의/실계좌 표시가 있는가. 푸터 운영자 표기가 필명인가.
> - 관리자 화면: 좌측 메뉴를 전부 열어 **빈 화면·에러·"목업" 문구**가 없는지 본다.
> - 버튼: 각 화면에서 대표 버튼 하나씩 눌러 **실제로 상태가 바뀌는지** 확인한다.
>   ⚠ 되돌릴 수 있는 것만 누른다. **삭제·발행·정책 스위치는 누르지 않는다.**
>   확인용 시드 데이터가 있으면 그것으로 시험하고, 시험 후 원래 상태로 되돌린다.
> 화면 이름과 관찰한 사실만 적어라. 코드 추측은 하지 마라.

**Workflow 스크립트 형태** (셋을 병렬로, 각자 스키마로 결과를 받는다):

```js
export const meta = {
  name: 'woodsman-site-inspect',
  description: 'Woodsman 운영지침 준수·보안·화면을 병렬 점검',
  phases: [{ title: '점검' }, { title: '검증' }],
}
const FINDINGS = { /* {findings:[{area,severity,where,what,why,fix}]} JSON Schema */ }
const [ops, sec, ui] = await parallel([
  () => agent(OPS_PROMPT, { label: '운영지침', phase: '점검', schema: FINDINGS }),
  () => agent(SEC_PROMPT, { label: '보안',     phase: '점검', schema: FINDINGS }),
  () => agent(UI_PROMPT,  { label: '화면',     phase: '점검', schema: FINDINGS }),
])
```

높음·중간 심각도 발견은 **검증 단계**를 한 번 더 붙인다 — 다른 에이전트가 반증을 시도해서
살아남은 것만 보고한다. 그럴듯하지만 틀린 지적이 한 번 섞이면 다음 점검을 아무도 안 믿는다.

## 3단계 — 보고

심각도 순으로 묶어 **표 하나**로 낸다. 항목마다: 무엇이 / 어디서 / 왜 문제인지 / 처방.

- 발견이 없으면 "없음"이라고 적되, **무엇을 봤는지 목록은 남긴다.** 안 본 것과 괜찮은 것을
  구분하지 못하면 점검이 아니다.
- 건너뛴 점검(로그인 안 함, 네트워크 실패 등)은 반드시 **따로 적는다.**
- 문서와 코드가 어긋나면 **양쪽 다** 제시하고 어느 쪽을 고칠지 사용자에게 묻는다.

## 4단계 — 기록

`docs/점검기록_YYYY-MM-DD.md`로 남긴다. 형식은 `docs/작업기록_2026-08-06.md`를 따른다.
같은 날 다시 돌리면 그 파일에 이어 쓴다.

지침 자체를 고치기로 했으면 `docs/운영지침.md`를 그 자리에서 갱신하고,
왜 바꿨는지를 `web/CHANGELOG.md`에도 한 줄 남긴다 — **문서가 뒤처지면 다음 점검이 거짓말을 한다.**

---

## 하지 않을 것

- 점검 중에 코드를 고치지 않는다. **발견과 처방까지가 점검이다.** 고치는 건 별도 지시로.
- 취약점 악용 코드(PoC)를 작성하지 않는다. 어디가 뚫리는지 지목까지만.
- 사용자 대신 로그인하지 않는다. 자격증명을 입력·저장하지 않는다.
- 운영 데이터를 지우거나 정책 스위치를 바꾸지 않는다. 되돌릴 수 있는 확인만 한다.
