# system-check — 묻기 전에 점검하고, 어색한 것만 말한다

## 왜 이 스킬이 있나

운영자(2026-09-27): 「항상 시스템 점검은 자동으로 해 주고, 어색한 것은 알려 주세요.」

첫 실행에서 바로 잡힌 것: **연방기금 선물(`zq_front`)이 9/20부터 8일째 수집 실패**였다. 홈 「금리 방향」 카드가
9/18 값에 멈춰 있었는데, 관리자 계기판에만 떠 있어서 아무도 몰랐다. 같은 날 아침 (70) 확인을 하면서도 놓쳤다 —
**보려고 한 것만 보면 나머지는 안 보인다.** 그래서 전체를 기계로 훑는다.

`site-inspect`(운영지침·보안 깊은 감사, 에이전트 세 갈래)와 다르다 — 이건 **가볍고 매번** 도는 건강 점검이다.

## 언제 (자동)

1. **세션 시작** — 「어제 이어서」 「오늘 할 일」을 볼 때 맨 먼저.
2. **배포 성공 직후** — release-log 스킬 다음.
3. **작업을 끝내기 전** — record-keeping 스킬과 함께.

## 절차

1. `cd web && node scripts/system-check.mjs` — 종료코드 0 = 어색한 것 없음, 1 = ⚠ 있음, 2 = 점검 실패.
2. ⚠가 있으면 **원인 한 단계만 더** 파고든다(예: 「수집 실패 1건」 → 어느 지표·언제부터·마지막 값). 추측으로 원인을 적지 않는다.
3. 사용자에게 **어색한 것만** 짧게 알린다 — 무엇이 · 언제부터 · 독자에게 무엇이 보이나 · 권고(고칠지/둘지). ✓ 목록은 늘어놓지 않는다.
4. 고치는 것은 **따로**다 — 점검 중에 고치지 않는다(변경은 하나씩 배포). 운영 데이터에 쓰는 일(적재·숨기기)은 운영자 확인 뒤.
5. 새로 알게 된 것은 기록한다(record-keeping) — 이어서 할 일(`pending-*.md`)에 올린다.

## 점검 항목을 늘릴 때

- 스크립트에 한 줄 더한다. 기준(몇 시간이면 늦었나)은 **상수와 이유**로 적는다.
- 사람이 놓친 것이 나오면 그것이 곧 다음 항목이다.

## 하지 않는 것

- 쓰지 않는다. 운영 D1·볼트 파일·티스토리 모두 **읽기만**.
- ✓만 잔뜩 보고하지 않는다. 「다 정상」이면 한 줄.
