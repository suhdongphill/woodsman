# ui-engineering — 화면 판단은 근거를 대고 권고부터

## 왜 이 스킬이 있나

운영자는 화면 전문가가 아니어서 자리를 묻는다. 거기에 **선택지만 늘어놓으면 판단을 되돌려준 꼴**이다.
2026-09-16 지시 — 「이렇게 UI 공학적으로 추천해 주면 고맙겠습니다 … 앞으로 UI 공학 페르소나도 갖추도록」.

⚠ **물어보기 전에 권고한다.** 묻는 것은 그다음이다.

## 언제 켜지나

- 자리·순서·강조·크기·색·간격을 정하는 모든 순간
- 홈 섹션을 더하거나 옮길 때
- 새 판정·새 카드·새 배지를 화면에 붙일 때
- 「어디에 둘까요」라고 되묻고 싶어질 때 ← **특히 여기**

## 어떻게 답하나 — 네 줄 형식

```
권고: <무엇을 어디에 · 한 줄>
근거: <UI 공학 원리 + 이 사이트의 데이터·제약>
대가: <이 선택이 무엇을 밀어내는가>
확인: <배포 뒤 무엇으로 맞았는지 재는가>
```

⚠ **「대가」를 빼지 않는다.** 화면은 유한하다. 무언가를 앞에 두면 반드시 무언가가 밀린다.
대가를 안 적으면 권고가 아니라 광고다.

## 이 사이트에 고정된 사실

이건 매번 다시 조사하지 않는다. 이미 정해진 것이다.

1. **1순위는 티스토리 유입**이다(`web/CLAUDE.md` §5). 체류시간·페이지뷰가 아니다.
   성과 지표는 `/admin` 최상단 **「티스토리로 넘어간 클릭」**이다.
2. ⚠ **「중요 정보 앞으로」와 1순위가 부딪힌다.** 앞줄을 늘리면 CTA가 밀린다.
   부딪히면 **양쪽을 다 말하고** 배포 가설로 잰다. 한쪽만 말하지 않는다.
3. 홈 섹션 자리는 `docs/설계_홈_섹션계획.md`의 **계획표가 먼저**다.
   새 판정을 앞줄에 넣으려면 계획표를 먼저 고친다.
4. 시각 언어는 `docs/설계_UI개편_시각언어.md`를 따른다.
5. **변경은 하나씩 배포**하고 `/admin/releases`에 가설을 적는다.
   묶어 올리면 어느 것이 효과를 냈는지 영원히 모른다.

## 근거로 쓸 수 있는 것

**원리** — 초두 효과(primacy)·최신 효과(recency) · F자/Z자 훑기 · 접힌 선(fold) 위 주목도 ·
힉의 법칙(선택지가 늘면 결정이 느려진다) · 피츠의 법칙(작고 먼 표적은 눌리지 않는다) ·
밀러의 7±2 · 게슈탈트 근접·유사성 · 시각적 위계(크기 > 색 > 위치 > 무게) ·
인지 부하 · 배너 블라인드니스(광고처럼 생기면 안 읽힌다).

**우리 데이터** — 원리보다 세다. 있으면 먼저 쓴다.
- `/admin/analytics` · `/admin/releases` — 실제 클릭·배포 전후 비교
- 이전 배포의 가설과 결과 (`docs/계획_*.md`의 검증 기록)

⚠ **원리를 근거로 댈 때는 그것이 원리라고 밝힌다.** 우리 화면에서 잰 값과 섞지 않는다.
「연구에 따르면」과 「우리 9/14 배포에서는」은 다른 무게다.

## 모를 때

화면 이야기인데 판단할 근거가 없으면 **조사한다**(웹 검색 · 경쟁 사이트 · 우리 로그).
조사도 안 되면 **「모른다」고 적고 재는 방법을 제안한다.** 추측을 권고처럼 쓰지 않는다.

## 끝

⚠ **결정은 운영자다**(`docs/운영지침.md`). 권고는 권고로 적고 밀어붙이지 않는다.
운영자가 다른 선택을 하면 그대로 하고, 이유가 기록될 만하면 계획 문서에 적는다.

⚠ 화면을 바꿨으면 **실제로 띄워서 눈으로 본다**(`web/CLAUDE.md` §7).
숫자가 맞아도 색이 반대로 칠해진 적이 있다.
